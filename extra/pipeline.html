The DiGiKits pipeline and CI/CD

How an idea becomes running software at DiGiKits: small tasks, a branch, a pull request, automatic checks, a person's review, then an automatic deploy. Take this after Deploy an app to a cloud server. For the coach too: work through it side by side.

The pipeline: eight steps from idea to live

Every change, big or small, takes the same road. Nothing reaches the live server without passing automatic checks and a person's review.

Who does what

WhoTheir job in the pipeline
The planner (a person)Decides what to build next and splits it into small issues
The AI (Claude)Drafts code, tests and README changes in a branch, and explains errors
The developer (a person)Runs it, tests it on real hardware when needed, opens the pull request
CI (GitHub Actions)Runs the tests and builds on every pull request, every time, without forgetting
The reviewer (a person)Reads the change and decides whether it merges
CD (GitHub Actions)Deploys main to the server and checks it's healthy

The same rule as everywhere at DiGiKits: the AI drafts, people decide, and the tests and the hardware have the final word.

CI and CD in one picture

CI (continuous integration) means every change is tested automatically before it can join main. CD (continuous deployment) means that once it joins main, it goes to the server automatically, exactly the way you did by hand in the deploy session.

Every product starts from one template

DiGiKits keeps a template repo. Each new product repo is copied from it, so every project already has the same folders, a Dockerfile, a docker-compose.yml, an .env.example, a README, and the workflow file below. Nobody sets up CI from scratch twice.

my-product/
├── .github/workflows/ci.yml    ← the pipeline
├── src/                        ← the app
├── tests/                      ← the checks CI runs
├── Dockerfile
├── docker-compose.yml
├── .env.example                ← names only, no secrets
└── README.md

The workflow file, line by line

GitHub Actions reads any .yml file in .github/workflows/. This example is for a small Node app; other languages swap the install and test lines. Use the newest major version of each actions/… step when you copy it.

name: CI
on:
  pull_request:                 # CI: on every pull request
  push:
    branches: [main]            # CD: when something merges into main

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: 22
      - run: npm ci             # install exactly what package-lock says
      - run: npm test           # the checks
      - run: docker build -t app .   # prove the image still builds

  deploy:
    needs: test                 # only if test passed
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production     # can require a person to approve
    steps:
      - name: Deploy over SSH
        env:
          SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
          HOST: ${{ secrets.DEPLOY_HOST }}
        run: |
          install -m 600 /dev/null key && echo "$SSH_KEY" > key
          ssh -i key -o StrictHostKeyChecking=accept-new deploy@"$HOST" \
            'cd app && git pull && docker compose up -d --build'
          curl -fsS https://app.example.com/health

Secrets again: the SSH key and server address are stored in the repo's Settings → Secrets and variables → Actions, never in the file. GitHub hides them in logs. Give the deploy key its own server user with only the access it needs.

Guard rails on main

  • Protect main (Settings → Branches): no direct pushes; every change goes through a pull request.
  • Require checks to pass before the merge button turns green.
  • Require one review by a person who didn't write the change.
  • Small pull requests: one issue, one branch, one pull request. Small changes are easy to review and easy to undo.

Hands-on

1. A practice repo with CI only

Make a new practice repo (or copy the template your coach shows you), add a tiny app with one test, and add the workflow file without the deploy job. Push it and open the Actions tab: watch your first run go green. GitHub Actions is free for this.

2. Break it on purpose

Open an issue, make a branch, change the code so the test fails, and open a pull request. Watch CI turn red and block the merge. Fix it, push again, and watch it turn green.

git switch -c fix-greeting
# edit, commit
git push -u origin fix-greeting   # then open the pull request on GitHub

3. Protect main

Turn on branch protection with required checks. Try to push straight to main and see it refused.

4. Add CD (with your coach)

Using the practice server from the deploy session, add the deploy job and the two secrets. Merge a small change and watch it reach the server on its own. Then make a change that fails the health check and practise the rollback: revert the pull request on GitHub, and the pipeline deploys the previous version.

When it breaks

What you seeLikely causeTry this
Workflow never startsFile not in .github/workflows/, or a YAML indent mistakeCheck the path; YAML uses spaces, never tabs
Test passes on your computer, fails in CIMissing install step, or a file that's only on your machineRead the failed step's log from the top
Deploy job skippedIt was a pull request, not a push to mainThat's correct: deploy runs only after merge
"Permission denied (publickey)"Deploy key secret wrong, or its public half not on the serverCheck the server user's authorized_keys
Deployed, but the site is brokenA bug the tests didn't catchRevert the pull request, then add a test that would have caught it

Done when

  • I can draw the eight-step pipeline from memory and say who does each step
  • My practice repo has a green CI run
  • I opened a pull request that CI blocked, then fixed it
  • main is protected with required checks
  • With my coach: a merge deployed itself to the practice server
  • I practised a rollback by reverting a pull request
  • No secrets anywhere in the repo or its history
