Stateless by design

A model is a function: context in, tokens out. The weights are frozen at inference time, so no conversation teaches the model anything.

A "chat" is an illusion built by the harness. On every turn, the full transcript so far is sent again, and the model reads it from the top as if for the first time. The fresh copy of the expert starting a new shift is literal.

This is a feature, not a limitation:

  • Isolation. One user's data never leaks into another user's session through the model itself.
  • Reproducibility. Same context in, same distribution of outputs.
  • Control. Everything the model knows about your situation sits in a context window you assemble and can inspect.

The practical consequence: if behaviour is wrong, look at what was in the context before blaming the model.

The client file: context assembly

"AI memory" is retrieval, not learning. The system stores facts outside the model and injects the relevant ones into the context before the call. A typical context window is assembled from:

  1. System prompt — the hat: role, rules, output format.
  2. Memory — durable facts about the user or project, pulled from a store.
  3. Retrieved documents — search results, RAG chunks, files.
  4. Tool results — sensor readings, API responses, database queries.
  5. Conversation history — the transcript so far, possibly summarized.
  6. The current request.

The expert reading the file very fast is exactly this: an open-book exam where your system chooses the book.

Fine-tuning is the other path: sending the expert back to school to change the weights. It suits stable style or format needs. For facts that change, retrieval almost always wins, because you can update a file in seconds and a model only by retraining.

The receptionist: the harness

The harness is where most of the engineering lives. The model is a commodity you rent; the harness is what you build. Its jobs:

  • Identify the user, session and task.
  • Decide what to retrieve, and how much.
  • Rank, trim and order what goes into the window.
  • Route tool calls and feed results back.
  • Decide what to write back to memory afterwards.

The two classic failures map straight to the metaphor.

The wrong file. Retrieval returns a near-match from another project, and the model answers fluently from it. The model did its job; the retrieval did not. Fix it with better keys, metadata filters and scoping.

The whole cabinet. Everything is stuffed into the window "just in case". Long contexts degrade: models attend less reliably to material buried in the middle, and irrelevant text competes with the relevant. This is often called context rot. More context is not free accuracy; past a point it is noise.

A good harness hands over the smallest context that fully answers the request.

The bill: tokens in, tokens out

The firm charges by the page. In AI, the page is the token (roughly three-quarters of an English word), and you pay for input tokens (everything the model reads) and output tokens (everything it writes).

The surprise for most teams is that input dominates. Because the transcript is resent every turn, a conversation's cost grows with its length on every single call. Ask a one-line question at turn 40 of a cluttered session, and you pay for the model to reread all 40 turns plus every attached file. That is the client who wanted one date fixed and got billed for ten years of paperwork.

Levers that keep the bill honest:

  • Scope retrieval. Pull the relevant chunks, not whole documents.
  • Prompt caching. Stable prefixes (system prompt, reference docs) can be cached, so repeated reads cost less and run faster.
  • Compaction. Summarize old turns instead of carrying them verbatim.
  • Fresh sessions. Start a new conversation when the task changes.
  • Right-size the model. Not every hat needs the most expensive expert; route routine jobs to smaller models.

Cost, latency and accuracy all improve together when the context gets smaller and sharper.

Where the metaphor breaks

The firm is a useful model of the system, but three differences matter for engineering.

Calibration. A human expert usually knows when they are guessing. A model produces fluent text whether or not it is grounded, and its confidence in tone is not a reliable signal of correctness. Fabricated details (hallucinations) look exactly like real ones.

Nondeterminism. Sampling means the same context can produce different outputs. Two runs of the same expert may give two different answers. Design for the distribution, not the single sample.

No lived experience. The model has seen descriptions of a motor running hot, never the smell. It knows the pattern, not the consequence.

The engineering answer is verification, built into the system rather than left to hope:

  • Ground answers in retrieved sources and require citations.
  • Validate outputs against schemas, tests and rules.
  • Run evals on real cases before and after every change.
  • Keep a human reviewer where an error is expensive.

Treat the model like a smart coworker whose work goes through review.

When the firm touches the physical world

On a screen, a wrong answer costs a revision. On a machine, it can cost a motor, a batch or a finger. Physical AI changes where the safety has to live.

The rule: the model proposes; something deterministic disposes.

  • Tool calls, not raw control. The model calls narrow, typed functions (set_speed(rpm)), never free-form commands to hardware.
  • Limits outside the model. Range checks, rate limits and state checks run in firmware or a controller the model cannot talk its way past.
  • Hardware interlocks stay hardware. E-stops, limit switches and thermal cutoffs never route through the AI.
  • Humans approve the irreversible. Anything that cannot be undone waits for a person.
  • Sensors are context too. A lying sensor is a wrong file; validate readings before the model reasons on them.

This is where the hot-stove knowledge matters. Someone has to know which failures are cosmetic and which are dangerous, and design the boundary accordingly. The model brings the patterns. The engineer brings the scars.

Careful what you specify

Models optimize for what you ask, literally. "Make my company more efficient" can return a plan that cuts the meetings that held the team together. That is specification gaming: the objective was met, the intent was not.

Ambition sets the objective. Constraints keep it pointed at what you meant.

UnderspecifiedSpecified
"Make it faster.""Cut cycle time without raising the defect rate."
"Reduce costs.""Reduce costs while holding customer satisfaction."
"Automate this.""Automate the routine steps; route final decisions to a human."

The same principle scales to agents: give them big jobs, explicit success criteria, explicit limits, and a way to stop and ask.

The real lesson

The model is the expert. It is brilliant, stateless and rented by the page.

Everything that makes it useful to you specifically, the file, the receptionist, the limits and the review, is system design. That is where the leverage is, and where the mistakes are.

AI doesn't become smarter because it remembers you. It becomes more useful because the system hands it a better briefing package, and pays for nothing it doesn't need.
