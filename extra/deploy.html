Deploy an app to a cloud server

Take a small web app from GitHub and get it running on a cloud server with its own web address and HTTPS. This is the same job DiGiKits does every time a tool goes live. Best done after Phase 2 Days 5, 8 and 9 (ports and Docker). For the coach too: work through it side by side.

What "deploy" means

Code on GitHub does nothing by itself. Deploying means copying it to a computer that is always on, starting it, and giving people a way to reach it. That always-on computer is a cloud server. DigitalOcean calls one a Droplet: a Linux computer in a data centre that you rent by the month and reach over SSH, just like your Pi.

The five parts of a deployment

PartWhat it doesYou met it in
DropletThe always-on Linux computerPhase 1 (Linux, SSH)
Domain + DNSTurns a name like app.example.com into the server's IP addressPhase 1 Day 6
FirewallOnly lets in SSH (22), web (80) and secure web (443)Phase 2 Day 5
Docker ComposeStarts the app and keeps it running after a rebootPhase 2 Days 8–9
Reverse proxyCaddy takes web traffic, adds HTTPS for free, and passes it to the appNew today

The one rule: secrets never go in Git

Passwords, API keys and login secrets go in a file called .env on the server only. The repo holds a .env.example with the names and empty values, and .gitignore lists .env so it can never be committed by accident.

If a secret ever lands on GitHub, even for a minute, treat it as stolen: make a new one and delete the old one. Never paste secrets into chats, the message board, or an AI.

# .env.example  (this one IS in Git: names only, no values)
DOMAIN=app.example.com
APP_SECRET=

Practise for free first

A Droplet costs money every month it exists. Do the whole session once on your Pi at home (steps 3 to 6 work the same on Raspberry Pi OS). Skip the domain and HTTPS, and open http://<pi-ip>:8080 instead. Only rent a Droplet when your coach says so, and destroy it when you're done practising.

Hands-on: the deployment, step by step

The example uses made-up names: the server 203.0.113.10, the domain app.example.com, and a practice repo your coach gives you. Swap in the real ones your coach gives you.

1. Create the Droplet

In the DigitalOcean control panel: Create → Droplets. Pick Ubuntu LTS, the smallest plan, the Toronto region, and SSH key login (paste your public key from Phase 1 Day 4, never the private one). Write down the IP address it gives you.

2. Point a name at it (DNS)

At the company that manages the domain, add an A record: name app, value = the Droplet's IP. It can take a few minutes to an hour to spread. Check it from your Pi:

dig +short app.example.com     # should print 203.0.113.10

3. Log in and lock the door

ssh root@203.0.113.10
adduser deploy                      # a normal user for daily work
usermod -aG sudo deploy
rsync -a ~/.ssh /home/deploy/ && chown -R deploy:deploy /home/deploy/.ssh
ufw allow OpenSSH
ufw allow 80,443/tcp
ufw enable
exit
ssh deploy@203.0.113.10             # from now on, log in as deploy

4. Install Docker

curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker deploy
exit                                # log out and back in so the group takes effect
ssh deploy@203.0.113.10
docker run --rm hello-world         # "Hello from Docker!" means it works

5. Get the app and its secrets

git clone https://github.com/<owner>/<practice-app>.git
cd <practice-app>/deploy             # DiGiKits repos keep the Compose file, Caddyfile and .env here
cp .env.example .env
openssl rand -hex 32                # makes a random secret
nano .env                           # paste it in, fill the other values, save

Every DiGiKits repo has the same layout (see the template), so every docker compose command on this page runs from the repo's deploy/ folder.

6. Start it and check it

docker compose up -d --build        # build and start in the background
docker compose ps                   # every service should say "running"
docker compose logs -f              # watch it start; Ctrl+C to stop watching
curl https://app.example.com/health

Caddy asks for an HTTPS certificate the first time someone visits. That only works once DNS (step 2) points at this server and ports 80 and 443 are open.

Updating, and undoing a bad update

cd <practice-app>
git pull
docker compose up -d --build

# Undo: go back one commit, rebuild, then fix the code calmly
git log --oneline -5                # find the last good commit
git checkout <good-commit>
docker compose up -d --build

Backups

  • The data: everything the app saves lives in its data/ folder. Copy it off the server regularly: scp -r deploy@203.0.113.10:~/<practice-app>/data ./backup-$(date +%F)
  • The whole server: DigitalOcean can take snapshots or weekly backups for a small fee. Take a snapshot before any big change.
  • The code and setup are already safe on GitHub. The .env is not, so your coach keeps the secrets in a password manager.

When it breaks

What you seeLikely causeTry this
Site doesn't load at allDNS not pointing here yetdig +short app.example.com and compare with the Droplet IP
HTTPS certificate errorDNS was wrong when Caddy first asked, or port 80 is blockedFix DNS or ufw status, then docker compose restart caddy
"port is already allocated"Another web server already uses 80/443sudo ss -tlnp | grep -E ':80|:443'; ask your coach before stopping anything
Container keeps restartingThe app crashes on start, often a missing .env valuedocker compose logs app and read the last lines
Can't SSH inFirewall enabled without OpenSSH, or wrong keyUse the Droplet's web console in the control panel

Use the fault-finding method from Phase 3 Day 2: one change at a time, and read the logs before guessing.

Where AI helps, and where it doesn't

Claude is good at writing the Dockerfile, the compose file and the README, and at explaining an error message you paste in. You still run the commands, read what comes back, and decide. Keep secrets, IP addresses and customer details out of anything you paste into an AI.

  • Made one update and one undo (rollback)
