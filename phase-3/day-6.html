AI as your support helper

Use AI to work faster, without letting it make mistakes in your name.

Remember Day 2

AI only knows what's in its "client file". Give it the right context, ask clearly, then check its work like a machine.

Ready for the next layer? Read How AI works: the firm, technical edition: context assembly, the token bill, and why limits live outside the model.

Claude at DiGiKits

Claude is the AI you'll use for support work. It's strongest when you hand it a good “client file”: five parts, every time.

Then do what you'd do with any coworker's suggestion: try the safest check first, and if Claude was wrong, say so and give it the new evidence.

Good uses

  • Explain an error message or log you don't recognise.
  • Draft a customer reply that you then edit.
  • Turn your rough notes into a knowledge-base article.
  • Suggest things to check next when you're stuck.

Rules

  • Never paste passwords, keys or a customer's private data into a chat.
  • Never run a command from AI that you don't understand, especially with sudo or rm.
  • You send the reply, so you own it. Read every word.

Practice

Solve two of your coach's broken systems with AI's help. Keep a log of what the AI said, what was right, and what was wrong.

A support prompt that works

Goal: find why a kiosk service fails at boot on a Raspberry Pi 5.
Context: Raspberry Pi OS (Bookworm, 64-bit), labwc desktop. Service file and log below.
  It worked until yesterday's apt full-upgrade. Starting it by hand works.
What I tried: daemon-reload, restart, checked the script path with ls -l (exists, executable).
Log (passwords replaced with XXXX):
  [paste the journalctl -b -u kiosk lines]
Ask: list the 3 most likely causes, most likely first, and for each the safest
  command to check it. Don't suggest anything that changes files yet.

Notice the last line: you ask for checks first, not fixes. You stay in control of what changes.

Clean a log before you paste it

ReplaceWith
Passwords, tokens, keys, Wi-Fi passwordsXXXX
Customer and person names, emails, phone numbersCUSTOMER, PERSON
Public IP addresses and internet names of client sitesPUBLIC_IP, SITE
Kuma push URLs and anything with a token in itURL_WITH_TOKEN

Private lab addresses like 192.168.50.50 are fine. When unsure, replace it.

Done when

  • Both fixed, and you caught at least one AI mistake before acting on it
  • Your prompt has goal, context, what you tried, a cleaned log and a clear ask
  • You cleaned a real log using the table above before pasting it
  • Your AI log lists at least one wrong suggestion and how you spotted it

More cases

Try each one before you open the answer.

Claude suggests sudo chmod -R 777 /home/tony to fix a permission error.

Big hammer: it would make every file writable by anyone (and break SSH keys). Ask for the specific file and owner instead, and fix that one (Phase 1 Day 5).

Claude's steps mention a menu that isn't on your Pi.

Likely written for another OS version. Tell it your exact version (cat /etc/os-release) and desktop (echo $XDG_SESSION_TYPE) and ask again.

You're about to paste a whole config file with a Wi-Fi password in it.

Stop. Replace the password with XXXX first, every time. If you already pasted a secret anywhere outside DiGiKits, tell your coach so it can be changed.
