Physical AI Systems · Lesson 7

Communication protocols: how the parts talk to each other

A Physical AI system is never one chip. Sensors, microcontrollers, a Pi, LED strips, a cloud server and a phone app all have to pass bytes to each other. A protocol is the agreed set of rules for doing that: which wire, how fast, what order, who speaks first. Watch a letter travel down a wire, then talk to devices on a bus.

Self-paced, so go easy on yourself. There are many protocol names in this lesson; you don't need to memorise them all today. Play with the drawings, and write what's unclear on the board below. Your coach goes through more examples with you in the live session.

A protocol is an agreement between people

Like a language, a protocol only works if both sides follow the same rules. Engineers wrote those rules down, gave them names, and every manufacturer builds to them. That's why a sensor made in one country works with a Pi made in another. Once again: by the people, for the people.

Three distances, three families

Watch a letter travel: UART

UART, often just called serial, is the simplest. One wire carries bits one after another. The line rests high. A start bit (low) says “here comes a byte”, then 8 data bits (lowest bit first), then a stop bit (high). Both sides must agree on the speed, called the baud rate, such as 115200 bits per second.

Many devices on two wires: I²C

I²C (say “I-squared-C”) lets one controller talk to many small devices over just two wires: SDA (data) and SCL (clock). Every device has an address, the hex numbers you met in Lessons 2 and 5. The Pi calls out an address; only that device answers. Click a device.

Fast and simple: SPI

SPI uses four wires: a clock, data out, data in, and a chip select wire for each device instead of an address. It's faster than I²C, so it's used for displays, memory chips and fast sensors. The cost is more wires.

MQTT: the noticeboard for devices

Many DiGiKits systems use MQTT to connect devices over the network. Instead of talking to each other directly, devices go through a broker, like a noticeboard. A sensor publishes a reading to a topic; anything subscribed to that topic gets it.

Hands-on

1. Read a frame

Send your initial in the UART drawing. Write down its 10 bits (start, 8 data, stop). Then tick the wrong-baud box and note which character arrives instead.

2. Scan the I²C bus

On the Pi, enable I²C (sudo raspi-config → Interface Options → I2C), then:

sudo apt install -y i2c-tools
i2cdetect -y 1          # a grid of addresses; a number means a device answered

With nothing connected the grid is empty, and that's a correct result too. If your kit has an I²C sensor or display, connect it and scan again.

3. Map a system

Pick a DiGiKits system you know (like the Big Screen or the LED controller) or any smart device at home. Draw the boxes and label each link with the protocol you think it uses. Post your drawing or a description on the board below.
