Microcontrollers in C++ (PlatformIO)

Write controller firmware the way DiGiKits does: C++ with the Arduino framework, built in VS Code with PlatformIO, on a Raspberry Pi Pico 2, reached over the network.

Why it matters

Every DiGiKits controller is a microcontroller plus a network device, with firmware written in C/C++. As support, you'll build, upload and check that firmware, and read it when something goes wrong.

You built the first version in Phase 1 Day 7. Today you learn to write and look after firmware properly.

How firmware runs

Never wait: millis() instead of delay()

delay(1000) freezes the board for a second: no commands are read, nothing else happens. Real firmware checks the clock instead. millis() gives the milliseconds since power-on; each time round loop(), you ask "is it time for the next step yet?". The board stays responsive while it animates.

Firmware with modes: src/main.cpp

#include <Arduino.h>
#include <Adafruit_NeoPixel.h>

const int STRIP_PIN = 2;
const int NUM_LEDS  = 30;
Adafruit_NeoPixel strip(NUM_LEDS, STRIP_PIN, NEO_GRB + NEO_KHZ800);

enum Mode { SOLID, RAINBOW };
Mode mode = SOLID;
unsigned long lastFrame = 0;          // time of the last animation step, in ms
uint16_t hue = 0;

void handle(Stream &port, String cmd) {
  int r, g, b, n;
  if (cmd == "OFF")          { mode = SOLID; strip.clear(); }
  else if (cmd == "RAINBOW") { mode = RAINBOW; }
  else if (sscanf(cmd.c_str(), "RGB %d %d %d", &r, &g, &b) == 3) {
    mode = SOLID; strip.fill(strip.Color(r, g, b));
  }
  else if (sscanf(cmd.c_str(), "BRIGHT %d", &n) == 1 && n >= 0 && n <= 255) {
    strip.setBrightness(n);
  }
  else { port.println("ERR " + cmd); return; }
  strip.show();
  port.println("OK " + cmd);
}

void listen(Stream &port) {             // never waits: returns at once if nothing arrived
  if (!port.available()) return;
  String cmd = port.readStringUntil('\n');
  cmd.trim();
  if (cmd.length()) handle(port, cmd);
}

void setup() {
  Serial.begin(115200);                  // USB: bench tests
  Serial1.setTX(0); Serial1.setRX(1);
  Serial1.begin(115200);                 // network module
  strip.begin();
  strip.setBrightness(40);
  strip.show();
}

void loop() {
  listen(Serial);                        // 1. listen on both doors
  listen(Serial1);
  if (mode == RAINBOW && millis() - lastFrame >= 20) {   // 2. animate: every 20 ms
    lastFrame = millis();
    hue += 256;
    strip.rainbow(hue);
    strip.show();
  }
}

Commands: RGB r g b, RAINBOW, BRIGHT 0–255, OFF. Every command answers OK … or ERR … on the same door it came in, so whoever sent it always knows whether it worked.

Wiring

The full chain, and where to test it

From your laptop: nc 192.168.50.60 5000, type RAINBOW. The Phase 2 Day 5 fake controller answered the same way on purpose: a script written against the fake works against the real controller unchanged.

Firmware updates

Firmware goes in over USB with PlatformIO. On site, a Pi or laptop next to the controller can build and upload it while you're connected over Tailscale. Your coach shows you the DiGiKits way of doing this; the rule is the same as every update: test on your own controller first, then canary (Day 12).

Done when

  • Your firmware runs RAINBOW and still answers commands while it animates
  • It answers on both USB and the network module
  • The project is in a GitHub repo with platformio.ini and without .pio/
  • You can name the test for each of the five links in the chain

Support drill

Your coach breaks one link in the chain. Find which, using the five tests above.

More cases

Try each one before you open the answer.

The build fails: “Unknown board ID 'rpipico2'”.

The platform = line still points at the standard Raspberry Pi platform, which doesn't know the Pico 2. Use the platform line above, save, and build again.

The strip animates, but commands take seconds to work.

Something blocks the loop, usually a delay(). Replace it with a millis() check so loop() comes round often.

Commands work in the Serial Monitor, not over the network.

Firmware is fine. Check Serial1 is started at the same speed as the module, the TX/RX wires aren't swapped, and the grounds are joined.

The board restarts every time the strip goes white.

The strip pulls power through the Pico's supply, so the voltage dips and the board resets. Separate supply for the strip, grounds joined.

After a power cut, the controller has a new IP and the kiosk can't find it.

The router reservation is missing or made for the wrong MAC. Reserve the module's address (Phase 1 Day 6) and note it in the site's network sheet.
