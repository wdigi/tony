Microcontrollers in C++ (PlatformIO)

Write firmware for a small microcontroller board the way DiGiKits does: C++ with the Arduino framework, built in VS Code with PlatformIO, on a Raspberry Pi Pico 2.

Why it matters

A Pi is a full computer. A microcontroller is a tiny one that runs one job, starts in a blink and almost never crashes. DiGiKits LED controllers use the same chip family as the Pico 2 (RP2350), with firmware written in C/C++. As support, you'll build, upload and check that firmware, and read it when something goes wrong.

You already ran the whole chain once in Phase 1 Day 7. Today you learn to write and look after firmware properly.

How firmware runs

Never wait: millis() instead of delay()

delay(1000) freezes the board for a second: no commands are read, nothing else happens. Real firmware checks the clock instead. millis() gives the milliseconds since power-on; each time round loop(), you ask "is it time for the next step yet?". The board stays responsive while it animates.

Firmware with modes: src/main.cpp

#include <Arduino.h>
#include <Adafruit_NeoPixel.h>

const int LED_PIN  = 0;
const int NUM_LEDS = 30;
Adafruit_NeoPixel strip(NUM_LEDS, LED_PIN, NEO_GRB + NEO_KHZ800);

enum Mode { SOLID, RAINBOW };
Mode mode = SOLID;
unsigned long lastFrame = 0;         // time of the last animation step, in ms
uint16_t hue = 0;

void handle(String cmd) {
  int r, g, b, n;
  if (cmd == "OFF")          { mode = SOLID; strip.clear(); }
  else if (cmd == "RAINBOW") { mode = RAINBOW; }
  else if (sscanf(cmd.c_str(), "RGB %d %d %d", &r, &g, &b) == 3) {
    mode = SOLID; strip.fill(strip.Color(r, g, b));
  }
  else if (sscanf(cmd.c_str(), "BRIGHT %d", &n) == 1 && n >= 0 && n <= 255) {
    strip.setBrightness(n);
  }
  else { Serial.println("ERR " + cmd); return; }
  strip.show();
  Serial.println("OK " + cmd);
}

void setup() {
  Serial.begin(115200);
  strip.begin();
  strip.setBrightness(40);
  strip.show();
}

void loop() {
  if (Serial.available()) {                  // 1. listen: never wait here
    String cmd = Serial.readStringUntil('\n');
    cmd.trim();
    if (cmd.length()) handle(cmd);
  }
  if (mode == RAINBOW && millis() - lastFrame >= 20) {   // 2. animate: every 20 ms
    lastFrame = millis();
    hue += 256;
    strip.rainbow(hue);
    strip.show();
  }
}

Commands: RGB r g b, RAINBOW, BRIGHT 0–255, OFF. Every command answers OK … or ERR …, so the Pi always knows whether it worked.

Wiring

The full chain: network → Pi → Pico → lights

Join today to your Day 5 fake LED controller. The Pi listens on the network and passes each line to the Pico:

# ~/practice/bridge.py  - network (Day 5) → Pi → Pico → LEDs
import socketserver, serial, threading

pico = serial.Serial("/dev/ttyACM0", 115200, timeout=2)
lock = threading.Lock()                      # one command at a time to the Pico

class Handler(socketserver.StreamRequestHandler):
    def handle(self):
        for line in self.rfile:
            cmd = line.decode().strip()
            with lock:
                pico.write((cmd + "\n").encode())
                reply = pico.readline().decode().strip() or "ERR no reply"
            self.wfile.write((reply + "\n").encode())

socketserver.ThreadingTCPServer.allow_reuse_address = True
socketserver.ThreadingTCPServer(("0.0.0.0", 5000), Handler).serve_forever()

Run bridge.py as a service (Phase 1 Day 9) and you have the shape of a real network LED controller.

Firmware updates without a trip

PlatformIO also runs on the command line, so a Pi on site can build and upload new firmware to its Pico while you're connected over Tailscale. Your coach shows you the DiGiKits way of doing this; the rule is the same as every update: test on your own Pico first, then canary (Day 12).

Done when

  • Your firmware runs RAINBOW and still answers commands while it animates
  • The project is in a GitHub repo with platformio.ini and without .pio/
  • A command typed on your laptop reaches the strip through bridge.py and the Pico
  • You can explain the difference between a Pi and a microcontroller, and why the timing goes on the Pico

Support drill

Your coach changes one thing in the chain (firmware, cable, wiring or bridge). Find which, using the four test points above.

More cases

Try each one before you open the answer.

The build fails: “Unknown board ID 'rpipico2'”.

The platform = line still points at the standard Raspberry Pi platform, which doesn't know the Pico 2. Use the platform line above, save, and build again.

The strip animates, but commands take seconds to work.

Something blocks the loop, usually a delay(). Replace it with a millis() check so loop() comes round often.

The board restarts every time the strip goes white.

The strip pulls power through the Pico's USB, or shares a weak supply, so the voltage dips and the board resets. Separate supply for the strip, grounds joined.

bridge.py says the port is busy.

The Serial Monitor (or another script) still has /dev/ttyACM0 open. Close it; only one program can use a serial port at a time.

Nothing arrives at the Pico after the Pi rebooted.

The Pico may now be /dev/ttyACM1. Check with ls /dev/ttyACM*. Real products use a fixed name from /dev/serial/by-id/ instead.
