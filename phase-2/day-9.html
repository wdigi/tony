Docker, part 2: Compose

Describe a whole app in one file and start it with one command.

📝Update progress on the message board below ↓

Why it matters

Real systems are several containers (web page, database, a worker). Compose keeps them together and restarts them after a reboot.

Practice

Create ~/dash/compose.yaml:

services:
  web:
    image: nginx
    ports:
      - "8080:80"
    volumes:
      - ./site:/usr/share/nginx/html:ro
    restart: unless-stopped
  uptime:
    image: louislam/uptime-kuma:1
    ports:
      - "3001:3001"
    volumes:
      - ./uptime-data:/app/data
    restart: unless-stopped
cd ~/dash
docker compose up -d
docker compose ps
docker compose logs -f uptime
docker compose pull && docker compose up -d   # update

Open Uptime Kuma on port 3001 and add monitors for your Pis and your fake LED controller (port 5000).

YAML rules that bite

  • Indent with spaces, never tabs. Items at the same level line up exactly.
  • Lists start with - (dash and a space).
  • Quote ports: "8080:80". Unquoted, some numbers with colons are read the wrong way.
  • Check before you start: docker compose config prints the file as Docker understands it, or the exact line that's wrong.

Compose commands

CommandDoes
docker compose up -dCreate and start everything in the background (also applies changes)
docker compose psStatus of this app's containers
docker compose logs -f webFollow one service's log
docker compose restart webRestart one service
docker compose exec web shShell inside a service
docker compose downStop and remove the containers (folders and volumes stay)
docker compose down -vAlso deletes named volumes. Data gone. Almost never on a customer system.

Settings and secrets: the .env file

Put values that change per site (and passwords) in a .env file next to compose.yaml. Compose fills them in:

# .env   (never commit this file: add it to .gitignore)
WEB_PORT=8080
KUMA_VERSION=1.23.16

# compose.yaml
services:
  web:
    ports:
      - "${WEB_PORT}:80"
  uptime:
    image: louislam/uptime-kuma:${KUMA_VERSION}

Same compose file on every site, a different .env on each. That's how DiGiKits ships one product to many clients.

Update and roll back

Healthchecks

A container can be "Up" but broken inside. A healthcheck lets Docker test it and show (healthy) or (unhealthy) in docker compose ps:

  web:
    image: nginx:1.27
    healthcheck:
      test: ["CMD", "curl", "-fs", "http://localhost/"]
      interval: 30s
      retries: 3

(The test command must exist inside the image. If it doesn't, the check fails even when the app is fine.)

Done when

  • Both containers come back after sudo reboot
  • Uptime Kuma shows red when you stop the fake controller
  • You validated your file with docker compose config
  • Port and version come from a .env file that isn't in Git
  • You updated a service to a new tag, then rolled it back
  • You can say what down -v deletes and why it's dangerous

Support drill

A container keeps restarting. Read its logs and find why.

More cases

Try each one before you open the answer.

“yaml: line 7: mapping values are not allowed in this context”.

An indentation or colon mistake near line 7: often a missing space after :, or a line indented by a different amount. docker compose config after each fix.

After docker compose down -v, Uptime Kuma lost all its monitors.

-v deleted the volumes. Restore from a backup if there is one. In our compose file Kuma uses a folder (./uptime-data), which down -v doesn't touch; named volumes are deleted.

docker compose ps shows a service “Restarting”.

Read docker compose logs servicename. Common causes: a wrong setting in .env, a port already used, or a volume folder with the wrong owner.

“Bind for 0.0.0.0:8080 failed: port is already allocated”.

Something else uses 8080: another container or app. sudo ss -tlnp | grep 8080, then stop it or change WEB_PORT.
