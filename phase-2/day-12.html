Phase 2 · Day 12

Managing many Pis

Look after ten Pis as easily as one.

📝Update progress on the message board below ↓

Why it matters

The lab and client sites have many computers. Doing everything by hand on each one is slow and causes mistakes.

Practice

Give each Pi a short name in ~/.ssh/config on your laptop:

Host screen1
    HostName trainpi
    User yourname
ssh screen1 uptime
scp file.txt screen1:~/              # copy one file
rsync -av ~/site/ screen1:~/site/    # copy a folder, only what changed
for h in screen1 screen2; do ssh "$h" 'hostname; vcgencmd measure_temp'; done

Use a second SD card (or a second Pi) as "screen2" so the loop really talks to two machines.

Names that tell you where and what

A fleet script

Keep the list of machines in a file, and one script that runs any command on all of them, in parallel, without hanging on a dead one:

# ~/fleet/hosts.txt
screen1
screen2

# ~/bin/fleet.sh
#!/bin/bash
# usage: fleet.sh 'command to run on every host'
while read -r h; do
  [ -z "$h" ] && continue
  ( out=$(ssh -n -o ConnectTimeout=5 -o BatchMode=yes "$h" "$1" 2>&1) \
      && echo "$h: $out" || echo "$h: FAILED ($out)" ) &
done < ~/fleet/hosts.txt
wait
fleet.sh 'vcgencmd measure_temp'
fleet.sh 'df -h / | tail -1'
fleet.sh 'systemctl is-active kiosk'

BatchMode=yes makes ssh fail instead of stopping to ask for a password. & and wait run all hosts at once.

Keep them the same

  • One golden image: set up one Pi perfectly, back it up (Phase 1 Day 10), and start every new screen from that image. Then only the name and site settings differ.
  • Settings in Git: service files, kiosk script, compose files. Push to every Pi with rsync, never edit one by hand on site.
  • Check for drift: fleet.sh 'cat /etc/os-release | head -1; uname -r'. One different answer = one Pi someone changed.

When the fleet grows, teams switch from a hand-made loop to a tool like Ansible, which describes "how every Pi should be" in files and makes it so. You'll meet it later; today's loop teaches the same idea.

Done when

  • One command shows the temperature of two Pis
  • You update a web page on both with one rsync loop
  • Your fleet.sh runs a command on two Pis in parallel and reports failures
  • Each Pi's hostname, ssh name and Tailscale name match
  • You can explain golden image, drift and canary

Support drill

The loop hangs on one machine. Add a timeout (ssh -o ConnectTimeout=5) and make it report which host failed.

More cases

Try each one before you open the answer.

The loop stops on one Pi and asks for a password.

That Pi doesn't have your key. Add it with ssh-copy-id. BatchMode=yes stops the loop hanging next time.

rsync with --delete removed the customer's own files from a screen.

--delete removes anything on the target that isn't in the source. Only use it on folders that belong entirely to us, and try --dry-run first.

An update broke all 12 screens at once.

Roll back with the backup or old version, then change the process: canary first, wait, then the rest.

Two Pis have the same hostname and keep swapping IPs in the router list.

One was cloned from the other without renaming. Rename one (sudo raspi-config → System → Hostname), reboot, update ssh config and Tailscale.
